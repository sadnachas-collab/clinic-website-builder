## Подключаем раздел «Доступы админов» к Lovable Cloud

Бэкенд уже готов: таблицы `admin_profiles` + `user_roles` (роли `owner` / `editor`) и серверные функции `listAdmins` / `createAdmin` / `deleteAdmin` / `changeOwnPassword` в `src/lib/admins.functions.ts`. UI в `public/clinic-admin.html` пока пишет только в localStorage — его и подключаем.

### Что меняем в `public/clinic-admin.html`

1. **Загрузка списка.** Добавляем `loadAdminsFromCloud()` — вызывает `listAdmins` и кладёт результат в `dbAdmins` в формате, который ждёт текущий рендер (`{ id: user_id, name: display_name, login, role: 'Владелец'|'Редактор', isOwner }`). Поле `pwd` в UI больше не показываем (пароль не возвращается с сервера, и это правильно).

2. **Добавление админа.** Перекрываем `saveAdmin` для новых записей (`isNew`): вызывает `createAdmin({ login, password, role: 'owner'|'editor', displayName })`. После успеха — `loadAdminsFromCloud()` + тост. Валидация (логин латиницей, пароль ≥6) уже есть в Zod-схеме на сервере, продублируем сообщения в UI.

3. **Удаление админа.** Перекрываем `deleteAdmin` — вызывает серверную `deleteAdmin({ userId })`, затем перезагрузка списка. Защиту «нельзя удалить владельца / самого себя» сервер уже проверяет.

4. **Смена своего пароля.** Если в UI есть поле смены пароля текущего пользователя (проверим при реализации) — подключаем к `changeOwnPassword`. Если нет — добавляем мини-форму в карточке текущего пользователя.

5. **Редактирование имени/логина существующих** в текущих серверных функциях не предусмотрено — оставляем только просмотр (поля readonly), либо в этой же итерации добавляем `updateAdmin` (см. ниже).

### Как iframe вызывает серверные функции

`clinic-admin.html` — iframe, у него уже есть `sb` (supabase-js с bearer из родителя). Серверные функции TanStack доступны по HTTP-эндпоинту `/_serverFn/<id>`. Вызываем через обычный `fetch` с заголовком `Authorization: Bearer <access_token>` (токен берём из текущей сессии `sb`). Это тот же токен, что `attachSupabaseAuth` прикрепляет в основном приложении — серверный middleware `requireSupabaseAuth` его примет.

Альтернатива — `postMessage` родителю и вызов через `useServerFn` в React. Дольше и без явных плюсов; идём через прямой fetch.

### Что НЕ трогаем
- Серверные функции `src/lib/admins.functions.ts` — не меняем (если только не добавляем `updateAdmin`, см. опцию ниже).
- Таблицы `admin_profiles` / `user_roles` / RLS — без изменений.
- Логин-флоу, seed первого админа, остальные разделы админки.

### Опционально (спросить у пользователя)
- **Добавить `updateAdmin`** (смена display_name / role / пароля другому пользователю owner'ом)? Сейчас этого нет — UI «Редактировать» для существующих строк будет ограниченным.
- **Поле «Роль»** в текущем UI — произвольная строка («Менеджер» и т.п.). На бэке только `owner` / `editor`. Предлагаю в UI заменить на select из этих двух значений.
