# Подключение Lovable Cloud к админке клиники

## Что делаем

Переносим админку с `localStorage` на реальную базу данных + добавляем настоящую авторизацию. Сейчас `/admin` открыт всем — после этого этапа войти сможет только админ с логином и паролем.

## Решения по вопросам

| Вопрос | Решение |
|---|---|
| Авторизация | Логин + пароль (без email). Под капотом — фейковый email `login@clinic.local`, заказчик видит только «Логин» |
| Первый админ | Сид-скрипт: `admin` / `123456`. Заказчик меняет при первом входе |
| Роли | `owner` (всё + управление админами) и `editor` (только контент) |
| Файлы | Два бакета: `photos` (публичные картинки) и `documents` (PDF/DOC) |
| Стартовые данные | Пустая БД, заказчик заполнит сам |
| Заявки | Таблица `requests` + раздел в админке. Интеграция с CRM — заглушка `sendToCRM()`, подставим код позже |

## Этапы работы

### 1. Включение Lovable Cloud
Активирую интеграцию. Появится БД, авторизация, Storage, секреты.

### 2. Схема БД (миграции)

Таблицы (примерно, точные поля — по факту того, что лежит в localStorage):
- `admins` — логин, роль (`owner`/`editor`), дата создания
- `services` — услуги (название, категория, цена, описание)
- `price_files` — загруженные прайс-листы (название, URL, дата)
- `specialists` — врачи (имя, должность, фото, описание)
- `reviews` — отзывы (имя, текст, рейтинг, дата, опубликован)
- `promos` — акции (заголовок, описание, картинка, период)
- `faq` — вопрос/ответ
- `interior_photos` — фото интерьера (URL, подпись)
- `documents` — документы клиники (название, URL, категория)
- `consumer_categories` + `consumer_documents` — уголок потребителя
- `authorities` — контролирующие органы
- `page_content` — контент главной, подвала, контактов (key/value JSON)
- `requests` — заявки с сайта (имя, телефон, услуга, комментарий, статус, дата)
- `user_roles` — роли (отдельная таблица, security definer функция `has_role`)

На каждой таблице — RLS:
- Публичные данные (услуги, врачи, отзывы и т.д.) — `SELECT` для всех
- Запись/удаление — только для `authenticated` с ролью `owner` или `editor`
- `requests` — `INSERT` для всех (форма с сайта), `SELECT`/`UPDATE` только для админов
- `admins` + `user_roles` — управление только для `owner`

### 3. Storage
Два бакета:
- `photos` — публичный, для картинок врачей/интерьера/акций
- `documents` — публичный, для PDF/DOC прайса и документов

RLS: чтение — всем, загрузка/удаление — только авторизованным админам.

### 4. Авторизация

- Страница `/login` (логин + пароль, без регистрации)
- При вводе логин превращается в `<login>@clinic.local`, идёт стандартный `signInWithPassword`
- `/admin` защищён: без сессии → редирект на `/login`
- Сид-скрипт создаёт первого админа `admin` / `123456` с ролью `owner`
- В админке раздел «Сотрудники»: `owner` может добавлять/удалять админов и менять роли
- Кнопка «Выйти» в шапке админки

### 5. Замена localStorage на запросы к БД

Во всех разделах админки и на публичном сайте:
- Чтение: `supabase.from('...').select()` вместо `JSON.parse(localStorage...)`
- Запись: `insert`/`update`/`delete` вместо `persistData()`
- Загрузка файлов: `supabase.storage.from('photos').upload()` вместо base64 в localStorage
- В БД хранятся только URL файлов

### 6. Раздел «Заявки» в админке

Новый пункт меню:
- Список заявок (имя, телефон, услуга, дата, статус)
- Фильтр по статусу: новая / в работе / обработана
- Кнопка «Пометить обработанной»
- Заглушка `sendToCRM(request)` в коде — точка интеграции с CRM заказчика

На публичном сайте форма «Оставить заявку» пишет в `requests` напрямую (RLS позволяет анонимный INSERT).

## Что НЕ меняем

- Дизайн админки и сайта
- Логику Quill-редакторов
- Кастомную модалку подтверждения удаления (уже сделана)
- Структуру разделов

## Технические детали

- Lovable Cloud = Supabase под капотом (БД + Auth + Storage)
- Роли через отдельную таблицу `user_roles` + security definer функция `has_role(user_id, role)` — это обязательно, иначе RLS зацикливается
- Все секреты (если понадобятся для CRM) — через секреты Lovable, не в коде
- Миграции SQL — отдельными файлами, каждая таблица с `GRANT` для `authenticated` и `anon` где нужно

## Что от тебя нужно после реализации

1. Залогиниться `admin` / `123456`, сменить пароль
2. Заполнить разделы реальными данными
3. Когда будет готов API CRM — дать мне эндпоинт и формат, я подставлю в `sendToCRM()`

## Объём работы
Большой этап. Делаю последовательно: Cloud → схема → auth → Storage → переезд разделов → заявки. После каждого блока — проверка, что ничего не сломалось.
